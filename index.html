Skynet FC (SKFC)

NVIDIA Isaac Sim과 ROS 2 Humble을 통합하여 입고 분류, 적재, 자율 이송(AMR), 포장 및 출고에 이르는 전 과정을 중앙에서 최적 스케줄링하고, PostgreSQL WMS와 Redis 실시간 캐시를 결합하여 구현한 스마트 디지털 트윈 관제 플랫폼입니다.

프로젝트 개요

지능형 다중 로봇 물류창고 관제 시스템의 핵심 아키텍처 및 동작 매커니즘을 소개합니다.

분산 제어와 중앙 스케줄링의 결합

본 시스템은 다수의 자율 주행 로봇(AMR)과 머니퓰레이터(Sorting, Stacking, Packaging)를 효율적으로 협업시키기 위해 중앙 집중식 하이브리드 제어 구조를 채택했습니다.

ROS 2 Action 통신망으로 AMR의 이송 명령을 제어하며, PostgreSQL 데이터베이스에 영구 적재 상태를, Redis 캐시 데이터베이스에 우선순위 큐(Sorted Set) 및 AMR 위치 정보를 수집하는 고성능 데이터 파이프라인을 구축했습니다.

  • 분산 월드 동기화: `TransitPackage.srv` 및 `WorkstationSimTrigger.msg` 토픽 채널을 활용해 분산 실행된 Isaac Sim 월드 간 실시간 조작 동기화
  • Double Buffer 및 Look-Ahead: 인바운드와 아웃바운드 라인에 각각 A/B 작업대 존을 구성하고 3슬롯/7슬롯에 도달 시 예비 작업대를 선제적으로 호출하여 로봇의 대기 오버헤드 차단
  • JIT 충돌 방지 인터로킹: 로봇 팔 기동 범주와 AMR 도킹 구역이 겹칠 시 180도 회전 명령을 내리고, 완료 전까지 로봇 기동을 일시정지(`pause_status`)하여 물리적 물건 드롭 방지
  • 리소스 및 주행 스케줄링: 동시 구동 AMR 대수를 최대 3대로 잠금 설정하고 Euclidean 거리를 활용해 가장 가까운 AMR을 우선순위 배정

창고 통로 주행 병목 및 데드락(교착) 현상

Aisle Congestion & Multi-Robot Deadlock

현상 및 분석
좁은 메인 보관 창고 통로(폭 1.5m)에 4대 이상의 AMR이 동시에 서로 다른 작업대를 이송하기 위해 진입하면서 헤드가 마주 보고 대기 상태에 빠져 주행이 영구 중단되는 교착 상태 발생.
원인
최단거리(Manhattan Distance) 경로 계획에 통로 내 AMR 가동 밀도에 대한 제약 조건이 누락되어, 이송 요청이 큐에 쌓이는 즉시 모든 AMR이 동시에 기동했기 때문임.
해결 및 구현
동시 기동 중인 AMR 이송 태스크 카운트를 실시간 모니터링하여, 동시 구동 대수가 3대를 초과할 경우 신규 이송 명령 하달을 차단하고 Redis ZSET 큐에 대기시키는 fleet limit 스케줄링 메커니즘을 도입함.
스케줄러 제약 코드 예시
# control_tower_node.py 내 대기 큐 및 가동 제한 체크
def execute_scheduler_tick(self):
    active_amr_count = self.get_active_workstation_move_count()
    if active_amr_count >= 3:
        self.get_logger().info(f'[Scheduler] AMR capacity full ({active_amr_count}/3). Redis 대기 task 유지')
        return

    # 우선순위가 높은 태스크부터 순차 팝하여 최단거리 AMR에 배정
    task = self.redis_client.zpopmax('queue:amr_tasks')
    if task:
        self.execute_amr_task(task)

동일 수령인 패키지 보관 오류 및 무한 적재 루프

Duplicate Recipient Address Resolution Loop

현상 및 분석
분류기에서 상자 스캔 시, 데이터베이스에 등록된 기존 동일 수령인의 이송 기록과 중복 매칭되어 분류 완료된 박스가 적재 작업대 대신 창고 직송(Direct-shipment)으로 오판정되고 시뮬레이터가 계속해서 같은 스캔 작업을 반복하는 무한 루프 발생.
원인
수령인의 고유 텍스트 필드(`customer_name`)로만 데이터베이스 히스토리를 쿼리하다 보니, 전날 완료된 동일 수령인 내역까지 오늘 대기 물량으로 오판정되어 Direct-shipment 액션이 비정상적으로 조기 트리거됨.
해결 및 구현
모든 쿼리와 분류 라우팅 상태 제어를 고유한 UUID 형태의 패키지 바코드 번호(`package_id`) 기반 조회로 변경하고, 합적 이송 콜백 수신 즉시 해당 상자의 WMS 상태를 `IN_WAREHOUSE`로 즉각 원자적 갱신하여 예외 상태 전이를 원천 차단함.

AMR 액션 서버 오프라인으로 인한 관제탑 교착 및 DB 상태 고착

Action Client Offline State Rollback Mechanism

현상 및 분석
AMR 물리 시뮬레이터(Isaac Sim) 혹은 ROS 2 Action 에뮬레이터 노드가 비정상적으로 느리게 구동되거나 네트워크 단절 시, 관제탑 노드가 작업대 목적지 스팟을 선점한 뒤 락(Lock)을 쥔 상태로 대기하여 데이터베이스 전체 이송 프로세스가 마비됨.
원인
Action Client가 Goal을 전송하기 위해 목적지 주차 스팟을 DB에서 `OCCUPIED`로 미리 업데이트했으나, 연결 타임아웃 발생 시 이 상태를 초기화(Rollback)하는 예외 트랜잭션 처리 구조가 없었기 때문임.
해결 및 구현
Goal 전송 대기 제한 시간(5초) 초과 혹은 거절 콜백 수신 시, 선점했던 목적 스팟은 `EMPTY`로 비우고 출발 스팟은 다시 `OCCUPIED`로 롤백하는 `recover_workstation_move_db_state()` 트랜잭션 복구 핸들러를 관제탑 노드에 직접 장착함.
복구 및 롤백 구현 코드
# control_tower_node_dispatch_limited_v6.py 내 실제 적용된 DB 롤백 핸들러
def recover_workstation_move_db_state(self, workstation_id, start, target):
    with self.get_db_connection() as conn:
        if conn:
            with conn.cursor() as cursor:
                # 1. 작업대 위치 및 상태 원상 복구
                cursor.execute(
                    "UPDATE workstations SET current_location = %s, status = 'WAITING', reserved_by = NULL WHERE workstation_id = %s;",
                    (start, workstation_id)
                )
                # 2. 출발지가 창고 스팟이었던 경우 다시 점유 상태로 복구
                if start.startswith('spot_') or start.startswith('stage_'):
                    cursor.execute(
                        "UPDATE warehouse_locations SET status = 'OCCUPIED', workstation_id = %s WHERE spot_id = %s;",
                        (workstation_id, start)
                    )
                # 3. 목적지가 창고 스팟이었던 경우 선점했던 공간 해제
                if target.startswith('spot_') or target.startswith('stage_'):
                    cursor.execute(
                        "UPDATE warehouse_locations SET status = 'EMPTY', workstation_id = NULL WHERE spot_id = %s;",
                        (target,)
                    )

720개 격자 DOM 렌더링에 따른 대시보드 웹 브라우저 스크롤 렉

High-Density DOM Reflow Optimization

현상 및 분석
웹 기반 실시간 관제 대시보드 구동 시 마우스 스크롤이 끊기고, WebSocket 업데이트 이벤트 수신 때마다 CPU 점유율이 90% 이상 치솟으며 웹 브라우저 전체 프레임레이트(FPS)가 10 이하로 저하됨.
원인
물류창고 격자 바닥을 표현하기 위해 720개 이상의 개별 HTML `div` 요소를 테이블/그리드 내에 동적으로 생성하고, 데이터 변경 시 전체 DOM 레이아웃의 Reflow/Repaint가 빈번하게 발생했기 때문임.
해결 및 구현
물리적 이동이 발생하는 핵심 노드(27개 스팟 및 로봇 영역)만 레이어 형태로 absolute positioning 하도록 요소를 95% 이상 축소하고, 컨베이어 라인은 고정 CSS 패턴으로 배경화하여 브라우저 DOM 연산량을 대폭 경감, 60fps 렌더링을 달성함.

영업일 종료(EOD) 직후 강제 플러시 예외 레이스 컨디션

End-of-Day Flush Gatekeeper Race Condition

현상 및 분석
특정 영업일 물량의 입고 CSV 명단이 업로드되어 분류가 시작되기도 전에, 관제탑 스케줄러가 이전 영업일의 마감(EOD) 처리를 감지하고 입고 라인의 빈 작업대들을 모두 포장존으로 강제 이송(Flush)시켜버려 입고 라인이 정지되는 오류 발생.
원인
"남은 대기 물량 0개" 감지 조건이 실제 오늘 분류 작업의 시작 여부(Inbound Started)를 판정하지 않고 단순 쿼리 개수로만 동작하여, 새 영업일 교체 및 CSV 대기 상황에서 레이스 컨디션을 유발했기 때문임.
해결 및 구현
Redis 캐시 메모리에 `system:inbound_started` Boolean 플래그를 신설하여, 관리자가 대시보드에서 공식적으로 '영업 시작' 버튼을 눌렀을 때만 8개 미만의 마지막 잔여 작업대 강제 플러시 트리거가 활성화되도록 보호 조건을 도입함.

ROS 2 멀티스레드 대기 상태 교착(Deadlock) 장애

ROS 2 Multithreaded Executor Deadlock Prevention

현상 및 분석
MultiThreadedExecutor 환경에서 특정 서비스나 액션 콜백이 내부적으로 다른 비동기 결과(Future)를 동기적으로 대기(spin_until_future_complete 등)하면서 스레드 풀의 가용 스레드를 소진하고 무한 대기하는 교착 상태가 빈번히 발생함.
원인
ROS 2의 스레드 스케줄링 특성상, 실행기 콜백 스레드가 블로킹되어 완료 대기하는 경우 다른 스레드가 완료 통지를 처리하지 못해 발생하는 스레드 풀 고갈 현상임.
해결 및 구현
콜백 스레드를 블로킹하지 않도록 call_async 호출 후 루프를 돌며 time.sleep(0.01) 등으로 스레드 제어권을 Executor에 명시적으로 양보하고 future.done()만 논블로킹 방식으로 체크하는 폴링 구조를 적용하여 데드락을 원천 해결함.
논블로킹 비동기 대기 코드
# 비동기 호출 후 논블로킹 방식으로 상태 체크 및 스레드 양보
future = self.cli_report_progress.call_async(req)
while not future.done():
    time.sleep(0.01) # 실행기 루프가 돌 수 있도록 양보
response = future.result()

작업대 정보 테이블 중복 슬롯 및 데이터 무결성 위반

Database Schema Normalization & Query Optimization

현상 및 분석
작업대와 패키지 정보가 어긋나 특정 작업대의 슬롯이 가득 찼음에도 WMS 데이터베이스 상에서는 빈 슬롯으로 나타나 적재를 추가 시도하다가 충돌하거나 누락되는 데이터 무결성 붕괴 발생.
원인
초기 WMS DB 설계 시 workstations 테이블에 slot_1_status, slot_1_customer 등 슬롯 컬럼을 1부터 8까지 직접 정의한 역정규화(Denormalization) 구조를 취하여 packages 테이블과의 매핑 상태 동기화 누수가 발생함.
해결 및 구현
workstations 테이블의 모든 슬롯 컬럼들을 제거하는 정규화(Normalization) 작업을 수행하고, packages 테이블에 workstation_id와 slot_number(1~8)를 외래키로 등록하여 JOIN과 서브쿼리로 슬롯 채움 상태를 실시간 뷰로 동적 도출하는 Single Source of Truth(SSOT) 아키텍처를 구현함.

Isaac Sim 바닥 Specular 반사로 인한 QR코드 카메라 디코딩 실패

USD Lighting Specular Glare & Vision Decoding Failure

현상 및 분석
시뮬레이션 구동 중 AMR이 바닥에 다다랐을 때 장착된 카메라 비전 센서에 하얗게 빛이 번져(Specular Glare) 텍스처 형태가 씻겨 나가면서 바닥 QR 디코딩 및 로컬라이제이션이 실패하고 탈선하는 오작동 발생.
원인
USD 씬 내부에 세팅된 기본 조명(DistantLight)의 방향성 조도가 3000.0 이상으로 지나치게 강하여 씬 평면의 난반사와 금속성 반사 필터 처리에 따라 반사광 오버플로우를 유발했기 때문임.
해결 및 구현
바닥 면의 Specular 반사를 잡기 위해 DistantLight의 강도를 600.0 수준으로 약화시키고, 대신 그림자를 상쇄하고 전체 조도를 고르게 유지해주는 1200.0 강도의 Diffuse DomeLight를 추가 구성하여 카메라 스캐닝 인식률 100%를 달성함.

PC 간 분산 실행된 Isaac Sim 환경의 상자 적재 및 순간이동 유실

Distributed Multi-Simulator Package Transit Synchronization

현상 및 분석
서로 다른 노트북에서 각각 실행 중인 BG2 입고 분류 시뮬레이션과 SG2 적재/포장 시뮬레이션 간에 상자가 연동되지 못하고 분류 라인 끝에서 낙하하거나 소멸되어 시뮬레이션이 연쇄 중단되는 장애가 발생함.
원인
각 물리 월드가 격리되어 있어, WMS DB에 패키지 입고 상태가 반영되더라도 3D 물리 공간 객체(USD Prim)의 소멸과 상대 월드로의 실시간 순간이동(Teleportation) 조작 채널이 유실되었기 때문임.
해결 및 구현
이송과 텔레포트 트레이싱을 전담 처리하는 sim_sync_node.py를 구축하고, 커스텀 ROS 2 서비스 TransitPackage.srv를 기동하여 패키지가 인바운드를 통과하는 즉시 원격 시뮬레이터 측으로 순간이동 API(USD Prim 생성 및 강제 좌표 변환)를 발행하고 DB 상태를 동기 업데이트함.
