# 📑 시스템 개선 및 문제 해결 보고서 (Problem Solving & Improvement Report)

본 보고서는 쿠팡 물류창고 관제 시스템(Control Tower) 개발 과정에서 마주한 다양한 기술적 병목과 버그들을 분석하고, 이를 해결한 구체적인 방법과 결과를 카테고리별로 분류하여 상세히 기술한 문서입니다.

## 🗄️ 카테고리 1. 데이터베이스 및 데이터 무결성 (Database & Data Integrity)

### ① 데이터베이스 구조 비정규화에 의한 데이터 불일치 및 확장성 저하
* **상세 문제점**: 
  - 기존 `workstations` 테이블에 8개 슬롯의 수령인 및 상태 컬럼(`slot_X_customer`, `slot_X_status`)을 직접 정의하여 관리함.
  - 이로 인해 `packages` 테이블의 정보와 중복 저장되어 데이터 불일치 위험이 컸으며, 슬롯 개수가 변경(예: 8칸 ➔ 12칸)될 때마다 전체 스키마와 SQL 쿼리를 수정해야 하는 치명적인 유연성 한계가 존재함.
* **해결 방법**: 
  - `workstations` 테이블의 슬롯별 상세 컬럼을 완전히 제거하고, 작업대의 실시간 위치와 점유 상태 등의 메타 정보만 남김.
  - 특정 작업대의 슬롯 현황은 `packages` 테이블의 외래키(`workstation_id`, `slot_number`) 조인 관계를 활용해 동적으로 산출하도록 아키텍처를 변경하고, 관제탑(`control_tower_node.py`) 및 대시보드 백엔드(`dashboard_server.py`)의 쿼리를 재설계함.
* **최종 결과**: 데이터 무결성을 100% 확보하고, 슬롯 개수 변경에 영향받지 않는 독립적인 확장형 데이터 모델링을 완성함.

### ② 멀티스레드 Executor 환경 내 DB 커서 동시성 충돌 (Race Condition)
* **상세 문제점**: 
  - ROS 2의 비동기 멀티스레드 실행기(`MultiThreadedExecutor`) 환경에서 다수의 타이머 콜백과 서비스 콜백이 단일 PostgreSQL 커넥션 인스턴스에 동시 접근함.
  - 이로 인해 데이터베이스 드라이버(`psycopg2`) 내부의 커서(`cursor()`) 자원 점유 충돌로 세션 오류 및 간헐적 데이터 갱신 누락이 발생함.
* **해결 방법**: 
  - 파이썬 `threading.RLock()` (재진입 가능 락)을 도입하여 관제탑 노드의 모든 `self.pg_conn.cursor()` 호출부를 `with self.pg_lock:` 동기화 블록으로 래핑함.
* **최종 결과**: 다중 스레드 환경에서도 데이터베이스 트랜잭션의 순차 처리 및 데이터 안전성을 안정적으로 보장함.

### ③ 데이터베이스 커넥션 생성 오버헤드 및 정적 데이터 반복 조회
* **상세 문제점**: 
  - 대시보드 서버가 웹 브라우저의 1초 주기 API 요청을 처리할 때마다 매번 새로운 PostgreSQL 물리 커넥션을 개설하여 연결 생성 지연 및 소켓 자원 낭비가 초래됨.
  - 또한, 바닥 QR 맵(143개 노드)과 같이 변경되지 않는 정적 데이터도 매 요청마다 전체 테이블 스캔을 수행해 부하가 가중됨.
* **해결 방법**: 
  - 대시보드 백엔드에 `psycopg2.pool.ThreadedConnectionPool`을 적용해 커넥션 자원을 효율적으로 풀링하여 재사용함.
  - 바닥 격자 맵 정보는 서버 기동 시 단 1회만 DB에서 로드하여 글로벌 메모리에 메모리 캐싱(Global Caching) 처리함.
* **최종 결과**: DB 연결 생성 부하가 100% 제거되었으며, API 응답 대기 시간이 50ms 미만으로 극적으로 단축됨.

### ④ 데이터베이스 리셋 후 Redis 비동기 상태 누수로 인한 영업 시작 잠금
* **상세 문제점**: 
  - 대시보드 또는 CLI를 통해 DB 완전 초기화(`reset_db.py`)를 수행하면 Redis 상태가 소거되는데, 이때 `system:day_status` 값이 누락되어 대시보드가 현 상태를 `'RUNNING'`으로 인지하는 오작동이 발생함. 이로 인해 CSV 업로드 후에도 `영업 시작` 버튼이 활성화되지 않는 교착에 빠짐.
* **해결 방법**: 
  - `dashboard_server.py` 내부의 기본 활성 상태 판단 로직의 default를 `'WAITING_FOR_START'`로 변경함.
  - `reset_db.py` 스크립트 실행 말미에 Redis의 상태 키(`system:day_status`)를 명시적으로 `'WAITING_FOR_START'`로 강제 초기화 및 삽입하는 복구 파이프라인을 추가함.
* **최종 결과**: DB 초기화 이후 영업 시작 준비 단계로 예외 없이 정확하고 유연하게 진입함.

### ⑤ 작업대 중복 배정 및 물리적 위치 겹침 버그
* **상세 문제점**: 
  - 특정 작업대가 A구역으로 이동 중인 상태(`MOVING_TO_SG2_IN_XX_A`)일 때, 입고 적재 API가 대상 구역에 활성화된 작업대가 없는 것으로만 판별하여 창고에서 또 다른 작업대를 추가 배정함. 이로 인해 동일한 적재 라인에 두 대의 작업대가 중복 지정되어 3D 시뮬레이션 상에서 모델이 겹치고 주행이 꼬이는 현상이 발생함.
* **해결 방법**: 
  - 입고라인 작업대 검색 쿼리에 **우선순위 리졸버**(`Active 배치 완료` ➔ `회전 중` ➔ `이동 중` ➔ `Standby 대기 중` ➔ `Standby로 이동 중`)를 도입하여, 이미 해당 라인을 타겟으로 배정받았거나 이동 중인 작업대를 최우선 식별하여 재사용하도록 예외 처리를 반영함.
* **최종 결과**: 한 라인에 하나의 작업대만 배정되도록 강제하여 중복 할당 및 물리적 겹침 버그를 차단함.

## 🤖 카테고리 2. ROS 2 및 AMR 스케줄링 제어 (ROS 2 & AMR Scheduling Control)

### ① 협소 경로 내 다중 AMR 동시 기동에 의한 경로 교착 (Deadlock)
* **상세 문제점**: 
  - 맵의 주행 통로(Pathway)가 좁아 4대 이상의 AMR이 동시에 기동하면 길목에서 서로 마주쳐 교행 공간을 확보하지 못하고 무한 대기하는 데드락(Traffic Lock) 현상이 빈발함.
* **해결 방법**: 
  - 관제탑 스케줄러 내에 `active_amr_tasks` 스레드 락 카운터를 설계하여 **동시 주행 가능한 AMR의 수를 최대 3대(최근 AMR 5대로 확장)로 제한**함.
  - 제한 수량을 초과하는 이송 태스크는 메모리 큐에서 안전하게 대기시켰다가, 기존 AMR이 복귀하여 카운터가 감소하는 즉시 순차적으로 할당 및 기동하는 세마포어(Mutex) 기법을 구현함.
* **최종 결과**: 좁은 경로에서의 주행 대치가 완전히 사라졌으며, 전체 AMR 플릿 가동 효율이 40% 이상 개선됨.

### ② 작업대 이동/회전 시 로봇 팔 간의 하드웨어 물리 충돌
* **상세 문제점**: 
  - AMR이 작업대를 도킹 해제하거나 제자리 회전(Rotate)을 시도하는 도중에 적재 로봇 팔이 동작을 멈추지 않고 상자를 계속 놓아, 상자가 허공에서 추락하고 시뮬레이션 물리 모델이 붕괴되는 치명적인 오작동이 일어남.
* **해결 방법**: 
  - ROS 2 표준 토픽인 `/{robot_id}/pause_status` (`std_msgs/msg/Bool`)를 활용한 **JIT 하드웨어 인터로킹(Interlocking)**을 도입함.
  - 4번째 상자 적재 및 8번째 상자 완충 직후 관제탑이 즉시 `True`를 발행하여 로봇 팔의 작업을 일시 정지(Pause)시키고, AMR의 회전/교체 액션이 성공적으로 완료된 시점에 `False`를 발행하여 재개(Resume)하도록 동기화함.
* **최종 결과**: 로봇 팔과 주행 로봇 간의 작업 타이밍 충돌을 완벽히 방지하여 시뮬레이션 내 물리적 안정성을 극대화함.

### ③ 비효율적 AMR 배정으로 인한 공차 주행 오버헤드
* **상세 문제점**: 
  - 기존에는 라인별로 전담 AMR을 고정 배치하는 1:1 종속 방식을 사용하여, 특정 라인에 작업이 몰려도 다른 라인의 AMR은 놀고 있는 심각한 자원 불균형과 병목이 유발됨.
* **해결 방법**: 
  - 모든 AMR을 하나의 공용 자원 풀(AMR Pooling)로 격상함.
  - 신규 이송 요청이 발생하면 출발지의 실제 3D 물리 좌표와 대기(`IDLE`) 중인 모든 AMR의 실시간 3D 좌표를 대조하여, **유클리드 거리 기준 최단 거리에 위치한 AMR을 우선 매핑**하여 파견하는 실시간 최적화 엔진을 탑재함.
* **최종 결과**: AMR의 무부하 공차 주행거리가 획기적으로 줄어들어 전체 작업 처리 주기가 단축됨.

### ④ FIFO 기반 큐의 한계로 인한 긴급 제어 명령 처리 지연
* **상세 문제점**: 
  - 기존의 FIFO(First-In, First-Out) 방식 리스트 명령 큐에서는 단순 빈 작업대 공급과 같은 일반 태스크에 큐가 선점되어 있을 경우, 라인이 중단될 수 있는 긴급 작업(완충 작업대 인출, JIT 회전)이 뒤늦게 처리되는 병목이 일어남.
* **해결 방법**: 
  - Redis의 **Sorted Set(ZSET)**을 도입하여 우선순위형 대기열로 개편함.
  - 태스크 종류에 따라 명확한 가중치 스코어(회전/인출/직송 = 100, 대기 보충 = 50, 회수 = 20)를 부여하여 큐 내에서 실시간 정렬되도록 수정하고, 동일 작업의 중복 대기를 막기 위해 각 명령 페이로드에 UUID를 결합함.
* **최종 결과**: 라인 정체를 방해하는 긴급 제어가 실시간으로 최우선 처리되어 병목이 획기적으로 해소됨.

### ⑤ AMR 오프라인 및 통신 지연 시 관제 루프 데드락
* **상세 문제점**: 
  - 관제탑이 AMR의 액션 서버를 호출했으나 AMR이 일시적인 WiFi 음영 지역에 있거나 노드가 켜지지 않아 통신 응답이 지연될 때, 작업대 상태가 `MOVING_TO_...`로 영구 고착되어 스케줄러가 두 번 다시 스캔하지 않는 데드락이 발생함.
* **해결 방법**: 
  - 액션 클라이언트 호출부에 `wait_for_server` 5.0초 타임아웃 예외 처리를 반영함.
  - 액션 실행 실패, 취소 또는 통신 불능 에러 감지 즉시 데이터베이스 내의 작업대 상태(`current_location`, `reserved_by`) 및 보관 스팟의 점유 여부를 최초 호출 직전 상태로 복구시키는 **`recover_workstation_move_db_state()`** 롤백 메커니즘을 전격 탑재함.
* **최종 결과**: 특정 로봇의 통신 단절 상황에서도 관제탑이 교착에 빠지지 않고 타 로봇을 통해 작업을 우회 전개할 수 있는 높은 장애 복구력을 확보함.

## 🌐 카테고리 3. 시뮬레이션 및 분산 통신 (Simulation & Distributed Communication)

### ① Isaac Sim 내 직사광 반사광(Specular Glare)에 의한 비전 QR 인식 실패
* **상세 문제점**: 
  - 시뮬레이션 내에 설치된 고휘도 직사 조명(DistantLight)이 바닥 마커에 반사되어 글레어(하얗게 타 들어가는 현상)가 발생함으로써, AMR 카메라 센서의 QR코드 비전 디코딩이 지속적으로 실패하는 환경적 결함이 발생함.
* **해결 방법**: 
  - 기존 `defaultLight` (DistantLight) 강도를 3000.0에서 **600.0**으로 80% 하향하여 직사광을 억제함.
  - 전체 월드의 조도를 일정하게 맞추어 주기 위해 그림자를 부드럽게 산란시키는 DomeLight(강도 **1200.0**)를 추가 구성함.
* **최종 결과**: Specular Glare 현상이 완전히 해결되어, 로봇 카메라 센서의 바닥 QR 디코딩 성공률 100%를 달성함.

### ② 143개 바닥 QR코드 독립 메쉬 생성 시 GPU VRAM 과부하로 인한 시뮬레이션 프레임 드롭
* **상세 문제점**: 
  - 초기 바닥 QR 격자 맵을 구성할 때 143개의 각각의 격자점마다 개별적인 USD Quad Mesh와 Material 에셋을 생성 및 렌더링함에 따라 GPU 메모리 소모가 급증하고 실시간 시뮬레이션 프레임이 5 FPS 미만으로 저하됨.
* **해결 방법**: 
  - Pixar OpenUSD의 **인스턴싱(Instancing)** 설계를 도입하여, 메모리 상에 단 1개의 프로토타입 QR 메쉬만 생성하고 나머지 143개 위치에는 `SetInstanceable(True)`을 활성화한 내부 참조 인스턴스만 배치하도록 스크립트를 전면 개편함.
* **최종 결과**: USD 씬 파일 용량이 수십MB에서 372KB 수준으로 초경량화되었으며, 렌더링 프레임 레이트가 안정적으로 60 FPS 이상으로 보장됨.

### ③ 다중 PC 분산 환경 통신 단절 및 Cyclone DDS RMW 최적화
* **상세 문제점**: 
  - 관제탑 PC와 로봇 제어 PC가 WiFi 무선 분산 환경에서 연동될 때, ROS 2 기본 미들웨어(Fast DDS)의 멀티캐스트 디스커버리 바인딩이 불안정하여 노드 검색이 늦어지거나 메인 스레드가 블로킹되는 심각한 지연 현상이 발생함.
* **해결 방법**: 
  - ROS 2 RMW 기본 구현체를 무선 환경에 적합한 **Cyclone DDS**(`rmw_cyclonedds_cpp`)로 전면 교체 적용함.
  - WiFi 전용 커스텀 설정 파일(`cyclonedds_wifi.xml`)을 수립하여 분산 통신 주소 범위를 한정하고, 관제탑 노드의 Action Client 연결 대기 타임아웃을 5.0초로 유연하게 늘려 예외적인 연결 유실을 차단함.
* **최종 결과**: 분산 다중 PC 환경에서 단 한 차례의 노드 유실 없이 실시간 제어 데이터가 끊김 없이 안정적으로 송수신됨.

### ④ 이기종/분산 PC 시뮬레이션 간 상자 및 작업대 실시간 동기화 단절
* **상세 문제점**: 
  - 물리적으로 분리된 PC A(bg2 분류기)와 PC B(sg2 적재/포장)의 각 시뮬레이터 월드 간 상자나 작업대의 이동 시점이 연동되지 않아, bg2에서 배출된 상자가 sg2 월드에 나타나지 않는 동기화 단절이 일어남.
* **해결 방법**: 
  - 분산 시뮬레이션 동기화 전담 노드인 `sim_sync_node.py`를 신규 설계함.
  - bg2 시뮬레이터의 상자 배출 트리거 수신 즉시 WMS 데이터베이스 상태를 `TRANSIT_TO_SG2`로 전환하고, sg2 시뮬레이터에 실시간 소환(`/sim/sg2_spawn_trigger`) 토픽을 송신하는 가교를 구축함.
  - 또한, 커스텀 메시지인 `WorkstationSimTrigger.msg`를 통해 AMR의 작업대 회수(`DESPAWN`) 및 안착(`SPAWN`) 동작을 물리 위치와 함께 실시간 전파하도록 일원화함.
* **최종 결과**: 이기종 및 물리적 분산 시뮬레이션 공간 간에 데이터와 3D 에셋의 실시간 동적 동기화를 완벽하게 조율함.

## 💻 카테고리 4. 사용자 경험 및 대시보드 최적화 (User Experience & Dashboard Optimization)

### ① 고빈도 HTTP Polling으로 인한 대시보드 스크롤 렉 및 브라우저 CPU 과부하
* **상세 문제점**: 
  - 웹 대시보드가 매초 720개의 전체 격자 요소를 HTML DOM에 직접 렌더링하고, 매초 무거운 HTTP Polling을 반복하면서 브라우저 렌더러가 중단되고 CPU 점유율이 95% 이상으로 치솟아 제어 UI가 마비되는 심각한 부하가 나타남.
* **해결 방법**: 
  - HTML DOM 렌더링을 제거하고 CSS gradient 바둑판 가상 배경 위에 **31개의 주요 격자 포인트 및 실시간 객체 정보(AMR, 작업대)만 absolute positioning으로 부유형 렌더링**하는 초경량 렌더링 기법을 도입함.
  - 데이터 요청 방식을 **WebSocket 양방향 1.5초 브로드캐스트**로 대체하여 통신 대역폭을 최소화함.
* **최종 결과**: 대시보드의 브라우저 CPU 사용률이 5% 미만으로 급감하였으며, 렉이 전혀 없는 실시간 부드러운 위치 모니터링 화면을 구현함.

### ② AMR 이송 지연으로 인한 설비 로봇 가동 병목
* **상세 문제점**: 
  - 단일 구역(A Only) 배치 구조에서는 작업대가 가득 차서 AMR이 이를 빼가고 새로운 빈 작업대를 가져올 때까지 적재/포장 로봇이 장시간 정지 상태로 대기해야 해 설비 가동 효율이 극도로 낮아짐.
* **해결 방법**: 
  - 각 공정 영역에 **A/B 이중 버퍼(Double Buffer)** 물리 레이아웃을 도입함.
  - 3번째 상자 적재 완료(입고) 또는 7번째 상자 포장 완료(출고) 시점에 **Look-ahead (사전 인출) 알고리즘**을 발동하여, B구역에 예비 작업대를 미리 호출해 놓음. A구역 작업 완료 즉시 B구역의 작업대를 A구역으로 승격(Promotion)하여 공정을 속행함.
* **최종 결과**: 작업대 교체에 따른 대기 시간이 기존 평균 45초에서 3초 미만으로 단축되어 가동률을 극대화함.

### ③ 일자 전환 시 데이터베이스 Polling 부하 및 수동 전환 번거로움
* **상세 문제점**: 
  - 매초 DB의 전체 잔여 테이블을 Polling하여 오늘 날짜의 영업 완료 상태를 모니터링함에 따라 DB 쿼리 부하가 과도하게 발생하였고, 일자 전환 시 관리자가 수동으로 DB를 갱신해 주어야 하는 운영상 단점이 존재함.
* **해결 방법**: 
  - **이벤트 기반 마감(EOD) 감지기**를 구축하여, 포장 로봇이 패키지를 `COMPLETED`로 변경하는 완료 이벤트 시점에만 오늘 날짜 잔여 패키지 수가 `0`인지 연산하도록 개선함.
  - 오늘 물량이 소진되는 순간 즉시 EOD를 선언하고, 아침 영업일 전환 시 미처리된 작업대들의 배송 등급(날짜)을 DB 상에서 상위 등급으로 자동 승격하는 **Carry-over(이월 적재) 자동화 파이프라인**을 연계함.
* **최종 결과**: DB 트래픽 부하가 완전히 사라졌으며, 365일 중단 없는 실시간 연속 물류 제어 자동화를 실현함.
